# ADR-001: Adoption of Relational Database (MySQL) with Modular Department Routing

* **Status:** Accepted
* **Date:** 2026-09-02
* **Authors:** Semaan

## Context
The **Internal Operations Service Hub** must manage ticket submissions, multi-department assignments (IT, HR, Facilities), and threaded activity/comments. We needed to choose a primary database architecture that guarantees data consistency, prevents lost updates, and supports relational queries across users, departments, and tickets. We evaluated a Document Store (MongoDB) versus a Relational DBMS (MySQL).

## Decision
We decided to adopt **MySQL** as the primary relational database system for the application.

## Rationale
1. **Relational Integrity:** Ticket ownership (`requester_id`), agent assignments (`assigned_agent_id`), and department routing require strict foreign key constraints to prevent orphaned records.
2. **Transactional Consistency (ACID):** Actions such as creating a ticket and logging an initial system comment must occur atomically within a single transaction.
3. **Structured Querying:** Filtering support tickets by status, department, and priority level relies on structured indexing and SQL joins, which MySQL handles efficiently.

## Alternatives Considered
* **Document Database (MongoDB):** While flexible for varying form fields, document stores make multi-entity joins and enforcing strict relational constraints more complex.

## Consequences
* **Positive:** Guaranteed data integrity, simplified relational queries, and strict schema validation.
* **Negative:** Any future schema changes (e.g., adding new custom columns) will require database migration scripts.
